# 书签点击次数（本地版）设计

日期：2026-11-18
状态：**已实现并归档**（原设计稿，实现过程中的偏离见文末「实现差异」）

> 归档说明：本文是 2026-11-18 讨论后定下的设计稿。实现过程中用户提出了几轮修改（保留期、展示位置、独立 tab），
> 最终形态与本文的差异集中列在最后的「实现差异」一节；正文保留原样以便追溯当时的取舍。

## 意图

知道每个书签从导航站卡片被真正打开过多少次（今日 / 本周 / 全部），用来清理长期不用的收藏。
v1 只写本机 localStorage，不改后端；上传 D1 留到以后。

## 目标

- 「点击卡片并跳转」= 一次使用；提供今日 / 本周 / 全部三个口径。
- 登录与未登录都记录（公开模式下常常不登录）。
- 每条统计带一个稳定的本机 id，为后续云端按设备汇总做准备。
- 设置 → 书签列表每行显示统计，可按「打开次数 / 最近打开」排序、可筛「从未打开」。
- 卡片 tooltip 显示次数，卡片布局不变。
- 纯本地、零请求、零 D1 变更。

## 非目标

- 不上传、不加 API、不改表结构（v1）。
- 不做全局「打开趋势」图表（第二阶段）。
- 不统计详情弹窗的打开按钮、浏览器扩展、右键、直接输入网址。
- 不跨设备 / 浏览器同步，不做「全站热度」。

## 约束与取舍

- 数据从功能上线起累积，无法回溯。
- 数字是「这台浏览器打开过多少次」；换设备 / 换浏览器各自独立，清站点数据即丢失。
- 访客的点击只写进访客自己的浏览器，不会进入你的数据，也不会影响你的展示。
- 同一浏览器上的多个账号共用一份本机统计（个人站点可接受）。

## 数据

`localStorage['bookmarkClickStats']`，整体一个 JSON：

```js
{
  v: 1,
  deviceId: "d_9f3a...",            // 本机 id，首次生成后稳定
  stats: {
    "1164": { c: 48, d: { "2026-11-18": 3, "2026-11-17": 7 }, t: 1763456000000 }
  }
}
// c = 本机全部累计（不裁剪）  d = 按天桶  t = 最后打开毫秒
```

- 今日 = `d[今天]`；本周 = 本自然周（周一 00:00 起）桶求和（与设置趋势图的周口径一致）；全部 = `c`。
- `deviceId` 用 `crypto.randomUUID()`，非安全上下文回退到时间戳 + 随机串；与统计同一个 key，清掉统计即视为新设备（避免旧设备水位把新数据压住）。
- `v` 留给将来迁移。

### 为什么带 deviceId

后续上传时按设备写**绝对值**，服务端按 `(device_id, bookmark_id)` 存一行并取 `MAX`：

- 重试、乱序回包都不会重复计数（增量方案必须额外维护水位，容易重复）。
- 换设备 / 清数据后 deviceId 变化会开新行，旧行保留，总和仍然正确。
- 服务端汇总用 `SUM`，不需要客户端做合并。

v1 不实现上传，只保证这个 id 现在就稳定存在。

## 模块

**`src/utils/clickStats.js`**（纯函数，Node 可测）

- `toDateKey(ms)` / `startOfWeekKey(ms)`
- `createClickState({ deviceId, now })`
- `parseClickState(raw, { now, makeDeviceId })` → 容错：损坏 JSON / 非法形状 / 缺 deviceId 时重建
- `recordClick(state, id, now)` → 新 state：`c+1`、今日桶 `+1`、`t=now`
- `getClickSummary(entry, now)` → `{ today, week, total, lastAt }`
- `pruneClickStats(state, { maxEntries })`

**`src/composables/useClickStats.js`**（与 `useLinkHealth` 同风格）

- 模块级 `reactive` state（含 deviceId），各组件共享
- `recordClick(id)`：不论登录与否都记录；localStorage 写失败只 `console.warn`，不影响打开网页
- `summaryOf(id)`
- 监听 `storage` 事件，其他 tab 的点击同步到本 tab 展示

**接线**

- `NavCard.handleCardClick`、`BookmarkCard` 的点击处理器：先 `recordClick(bookmark.id)` 再 `window.open`
- `NavCard`：展示使用次数（最终形态见「实现差异」）

**设置 → 书签 tab（`NavSettingsModal`）**

- 每行显示 `今日 2 · 本周 9 · 共 48`；全 0 显示 `未打开`（弱化色）
- 排序 / 筛选控件：默认 / 打开次数 / 最近打开 / 从未打开
- 排序与筛选只作用在现有分类分组内部，保留吸顶 header、增量渲染、搜索与分类筛选

## 方案与取舍

| 方案 | 内容 | 结论 |
|------|------|------|
| A 只放卡片 tooltip | 最省事，但基本看不到 | 弃 |
| B（采用）设置列表可见 + 排序/筛选 + 卡片展示 | 能支撑「清理不用书签」 | 采用 |
| C B + 逐次时间戳 / 全库时间线 Top 榜 | 数据无界、要裁剪、要改趋势 tab | 只做了单书签走势，全库榜未做 |

## 风险与已知问题

- 多 tab 同刻点击可能丢 1 次（读改写竞争），展示由 `storage` 事件收敛，可接受。
- 书签删除后统计残留，靠 2000 条上限淘汰，不做孤儿清理（避免与 `useBookmarks` 耦合）。
- 未登录也记录意味着公共设备上别人浏览公开站会留下本地数字；只影响那台设备自己的展示。

## 验收

- 登录或未登录点卡片：卡片数字 +1，设置行今日 +1，刷新后仍在。
- 首次写入生成 `deviceId`，之后保持不变；清空该 key 后重新生成。
- 跨天 / 跨周口径正确（单测覆盖）。
- 排序与「从未打开」筛选正确，分组、吸顶、增量渲染不破。
- `npm run test:clicks`、`npm run build` 通过。
- AGENTS.md 补充该功能说明。

## 实现差异（归档时补记）

按实现顺序，与上文不一致的地方：

1. **日桶不再裁剪**（原：裁掉 35 天前）。用户要求「一直保留」，只保留「条目数 > 2000 时按最后打开淘汰」。
   代价是体积随时间增长（约 17 字节/天桶），因此在点击 tab 显示「当前占用 xx KB」，并提供手动「清空」。
2. **卡片展示从 tooltip 改为 URL 行右端胶囊**：`1·12`（今日·总计），今日用主色、总计灰，总数为 0 不渲染。
   tooltip 保留「使用：打开 N 次 · 今天 N 次」作为无歧义对照。
3. **从「趋势」tab 拆出独立的「点击」tab**：趋势讲「新增书签」，点击讲「使用」，混在一页会被读成同一套数据。
4. **点击 tab 的形态**：四块汇总（今日/本周/总/用过的书签）+ 一份**全量**列表（所有有记录的书签）+ 排序（总次数 / 最近打开 / 今日）+ 搜索 + 行内展开 90 天走势 + 清空。
   - 期间一度只做「最常用前 10 + 最近打开前 5」，因为看不到全量、且最近打开是子集而被推翻。
   - 一度有「编辑」入口，因为统计页不该做管理而被移除，改为行尾 ↗ 直接打开书签。
5. **新增 `getClickTotals` / `getDailySeries` / `formatLastOpenedAt` / `clearClickStats`** 四个纯函数。
6. **详情弹窗**（`NavBookmarkEditModal`）标题下补一行 `今日 X · 本周 Y · 共 Z 次`。
7. **明确未做**：
   - 24 小时时段桶（`h`）——「晚上 8 点最常打开」这类问题需要新字段，且历史补不回来；
   - 全库点击趋势图——数据从上线才开始，前期画出来几乎是空图；
   - 云端同步（保持 v1 纯本地，`deviceId` 已预留）。

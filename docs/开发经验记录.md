# 开发经验记录

## Flex 表格布局对齐

**问题**：用 flex 布局做表格时，表头和数据行列错位。

**根因**：表头 `.tag-table-header` 和数据行 `.tag-row` 的 `gap` / `padding` 不一致。数据行有 `gap: 0.75rem`，表头没有，导致列位置不同。

**解决**：表头和数据行必须保持完全一致的 `gap`、`padding` 属性。

```css
/* 表头 */
.tag-table-header {
  display: flex;
  gap: 0.75rem;    /* 必须与 .tag-row 一致 */
  padding: 0.5rem 0.875rem;
}

/* 数据行 */
.tag-row {
  display: flex;
  gap: 0.75rem;
  padding: 0.5rem 0.875rem;
}
```

## 用 Console 诊断 CSS

**原则**：不要凭猜测改代码，先用浏览器控制台验证。

**常用命令**：

```js
// 1. 检查计算样式
const el = document.querySelector('.target-class')
const style = getComputedStyle(el)
console.log('display:', style.display)
console.log('justify-content:', style.justifyContent)
console.log('width:', style.width)

// 2. 检查元素实际位置和尺寸
const rect = el.getBoundingClientRect()
console.log('位置:', rect)

// 3. 比较两个元素的对齐
const elA = document.querySelector('.col-a')
const elB = document.querySelector('.col-b')
const rectA = elA.getBoundingClientRect()
const rectB = elB.getBoundingClientRect()
console.log('A x:', rectA.x, 'B x:', rectB.x, '差值:', rectB.x - rectA.x)
```

## 避免盲目反复修改

**反面案例**：本次会话中改了 8 次才找到根因（gap 不一致）。

**正确流程**：
1. 先跑 console 命令确认 CSS 是否生效
2. 用 `getBoundingClientRect` 确认元素实际位置
3. 对比表头和数据行的列位置差异
4. 找到差异后针对性修复

**经验**：一条 console 命令 5 分钟能定位的问题，反复猜测改代码可能花 30 分钟还修不好。

## CSS 动画不重新触发

**问题**：组件用了 `:key="xxx"` 强制销毁重建，但 CSS 入场动画只在首次加载时生效，切换分类后动画消失。

**根因**：
1. `onMounted` 触发时 `props.bookmarks` 可能还是空的（Vue 的 computed 和渲染有异步性）
2. `v-if="bookmarks.length > 0"` 控制的 DOM 元素在数据加载后才渲染，此时 `animationClass` 还是空的
3. Vue 的 key diff 可能复用 DOM 元素，CSS 动画不会重新触发

**错误尝试**：
- 用 `nextTick` 包裹 `animationClass` 赋值 → 无效，因为 `onMounted` 时 bookmarks 还是空
- 用 `{ immediate: true }` 的 watch → 无效，首次 watch 触发时 bookmarks 可能还没变化

**正确方案**：用 `watch` 监听数据实际变化，而不是依赖 `onMounted`：

```javascript
// NavCardGrid.vue
watch(() => props.bookmarks.length, (newLen, oldLen) => {
  if (newLen > 0 && newLen !== oldLen) {
    animationClass.value = ''
    requestAnimationFrame(() => {
      animationClass.value = 'animate-slideUp'
    })
  }
})
```

**关键点**：
1. 用 `watch` 监听 `bookmarks.length` 而不是 `onMounted`，确保数据已加载
2. `newLen > 0 && newLen !== oldLen` 只在有数据且变化时触发
3. 先清空再用 `requestAnimationFrame` 延迟设置，强制浏览器重置动画状态

**经验**：
- `:key` 强制重建 ≠ CSS 动画重新触发，Vue 可能复用 DOM
- `onMounted` 的执行时机不等于 props 已更新完成
- 涉及数据驱动的动画，优先用 `watch` 而不是 `onMounted`

## HTTP 200 不等于“探测成功”

**问题**：浏览器扩展用 `GET /api/ping` 测连接延迟，把服务器地址指向另一个 Cloudflare Pages 项目时，胶囊上显示的数字其实是**首页的下载时间**，甚至根本没测到网络。

**根因**：

1. Pages 的 SPA fallback 会把不存在的 `/api/ping` 重写成 `200 + index.html`；
2. Cloudflare Access 未登录时 302 到登录页，`fetch` 默认跟随重定向，最终拿到的还是 200；
3. 只判断 `response.ok`，就会把“首页首字节”当成网络延迟，完全看不出后端没有这个端点。

**解决**：探测端点必须校验响应体形状，而不只是状态码：

```js
if (!response.ok) return { ok: false }

// 先看 Content-Type，避免把整页 HTML 拉下来
const type = response.headers.get('content-type') || ''
if (!type.includes('application/json')) return { ok: false, unsupported: true }

const payload = await response.json().catch(() => null)
if (!payload || payload.ok !== true) return { ok: false, unsupported: true }
```

**经验**：

- 连通性探测 = 状态码 + 响应体形状 + 数据来源，只看状态码会把 SPA / 登录页误判成成功；
- 判定“不支持”后要降级并说明数字来源（如“延迟取自最近一次请求”），不能继续挂着上一次的成功值；
- 测延迟时不要和业务大请求并发，响应体与拥塞会污染结果——先等在途请求落地再测；
- 顺带一个工具坑：PowerShell 5.1 的 `Get-Content` 默认按 ANSI 读文件，UTF-8 文件会显示成乱码。判断编码要看字节（`[IO.File]::ReadAllBytes` 的前几个字节）或用 `[Text.Encoding]::UTF8.GetString()`，别急着做“编码转换”。
